# shikigami — 視覺語言規格

一個人、一隻式神、N 個 agent。這份文件定義式神在透明無邊框視窗上的完整視覺契約。

- `index.html` — 互動規格頁，在四種不可預測背景上跑完整套元素，弧形與扇形座標即時計算
- `tokens.css` — 可直接貼進 `src/styles.css` 的 `:root` 變數表與位置契約
- 本文件 — 推導、數值、落地清單

---

## 0. 一句話

> **冷色與無彩是給機器的，暖色是給人的。**

看到暖色 = 這裡有你的事。看到冷色 = 那是某個 agent 的狀態。
綠 `#34d399` 整組退出系統 —— 它同時是「工作中」和「可以點」，正是撞車的來源。

## 1. 色彩兩軸

### 1.1 狀態軸 — 只出現在狀態點與 orb

| 狀態 | OKLch | 近似 hex | 動態 | 形 |
|---|---|---|---|---|
| `idle` | `oklch(64% 0.005 250)` | `#9ba1a8` | 不呼吸 | 實心，縮至 `scale(0.72)` |
| `working` | `oklch(78% 0.130 200)` | `#40d3e8` | 呼吸 3.2s | 實心 |
| `blocked` | `oklch(68% 0.200 335)` | `#ef5cc4` | 心跳 1.6s（雙拍） | 中空環 2.5px |
| `done` | `oklch(89% 0.050 235)` | `#c9e3f7` | 靜止 | 實心，最亮 |

四種狀態同時靠 **色相、明度、動態、實心／中空** 四個維度分開。任一維度失效
（色盲、12px 太小、使用者關掉動態）都還剩三個。

`working` 青 200° 與 `done` 冷白 235° 色相僅隔 35°，但明度差 11 個點、飽和差 2.6 倍、
一個呼吸一個靜止 —— 在 12px 的圓點上仍可分辨。

`blocked` 從琥珀改為品紅 335°，兩個理由：把琥珀讓給介面軸；品紅離 `working` 的
青 200° 有 135°，是四色中最大的色相距離，而「卡住了」正是最需要被一眼認出的狀態。

### 1.2 介面軸 — 只出現在可操作物

| 意義 | OKLch | 近似 hex | 用在哪 |
|---|---|---|---|
| 可點（靜） | `oklch(93% 0 0)` | `#e9e9e9` | 所有按鈕文字與細邊 |
| hover / focus | `oklch(100% 0 0)` | `#ffffff` | 邊框轉白，底提亮 4% |
| 待你決定 | `oklch(80% 0.150 78)` | `#f4b23c` | **只有確認框**。別處出現即為錯誤 |
| 危險 | `oklch(64% 0.190 32)` | `#ef6a4a` | **只有選單的 Close** |

琥珀從 `blocked` 手上被收回，成為「等你」的獨佔色。這是整套設計最重要的一次收斂：
畫面上出現琥珀，永遠只有一個意思。

介面軸的主力是無彩色。可操作性靠 **明度與邊框** 表達，不靠色相 —— 於是它天然
不可能與狀態軸撞車。

### 1.3 在不可預測的背景上活下來

背後可能是白色文件、黑色終端、彩色桌布。解法不是挑一個「兩邊都還好」的顏色
（不存在），而是 **讓每個元素自帶不透明深底**，顏色永遠在自己的底上被看見。

| 技法 | 值 | 為什麼 |
|---|---|---|
| 深底 | `rgba(12,14,19,0.90)` + `blur(10px) saturate(1.2)` | 顏色與背景脫鉤 |
| 頂緣受光 | `inset 0 1px 0 rgba(255,255,255,.10)` | 在黑終端上把面板抬起來 |
| 外暗邊 | `0 0 0 1px rgba(0,0,0,.52)` | 在白文件上把面板從背景分離 |
| 狀態點隔離環 | `0 0 0 1.5px rgba(0,0,0,.55)` | 小色點沒有面板可躲，自己帶輪廓 |

**受光邊與外暗邊缺一不可**（表中第 2、3 列）：只有受光邊，面板在白文件上會像一塊
漂浮的髒污；只有外暗邊，面板在黑終端上會直接融進背景。

#### 實測對比度

深底 alpha 取 `0.90` 的後果是**合成底幾乎與背景無關** —— 這正是想要的性質，
也讓對比度可以一次算定而不必逐張桌布試。三種背景合成後的實際比值：

| 背景 | 合成底 | `--ui-fg` | `--ui-fg-dim` | `--ui-pending` | `--ui-danger` |
|---|---|---|---|---|---|
| 白文件 `#fdfdfb` | `rgb(36,38,42)` | 12.49:1 | 6.83:1 | 8.14:1 | 4.93:1 |
| 黑終端 `#0c0d0f` | `rgb(12,14,19)` | 15.91:1 | 8.71:1 | 10.38:1 | 6.28:1 |
| 彩色桌布（棕 `#7a5a48`） | `rgb(23,22,24)` | 14.89:1 | 8.15:1 | 9.71:1 | 5.88:1 |

門檻：內文 `≥ 4.5:1`、UI 元件 `≥ 3:1`（WCAG 2.2）。**最壞情況是白文件上的
`--ui-fg-dim` 6.83:1**，仍有 1.5 倍餘裕；四色三背景全數通過。

三種背景的合成底彼此只差 24 個亮度階，這是 alpha 0.90 的直接結果 ——
換句話說，換任何桌布都不會讓文字掉出門檻，不需要再測更多樣本。

但受光只有**頂緣一道**，不是一圈框 —— 一圈白框會與確認框的琥珀框打架，
也讓報告泡泡看起來像一個可以按的東西。框在這套系統裡是有語意的，見 §2.5。

## 2. 層級與位置契約

### 2.1 四套方向邏輯收成兩套

| 圈 | 成員 | 方向規則 |
|---|---|---|
| **內圈** | 狀態點 | **固定朝上**。永遠在視窗內，因此根本不需要方向邏輯 |
| **外圈** | 確認框、報告泡泡、名牌 | **朝螢幕中心**。三者共用同一個 flex 容器 |

這是本次最大的結構簡化。原本四個元素各有一套方向處理（報告上下翻轉、選單扇形
角度、狀態點固定朝上、確認框完全不翻轉），現在只剩「內圈不翻、外圈翻」兩類，
外圈的翻轉又只是容器上的兩個 class。

### 2.2 外圈堆疊順序（由 orb 往外）

```
        orb 輪廓  (idle r≈41 · 說話峰值 r≈56)
        ─────────────────────── 錨點：視窗中心 ±64
  slot 1  確認框      ≤ 120px   近緣 +64    主位。它是最後一關，必須貼著式神
        ─── gap 8
  slot 2  報告泡泡    ≤  66px   近緣 +192   次要，會自己消失
        ─── gap 8
  slot 3  名牌        ≤  20px   近緣 +266   最外
                                最遠緣 286
```

順序不是隨便排的：

- **確認框在最內** —— 它是主角，且必須讀起來是從式神本體長出來的。
- **名牌在最外** —— 它由 hover 驅動、出現頻率最高。放最外，它的出現就永遠不會
  推動已經在場的東西。這正是現有程式碼註解裡「showing it never moves the
  bubbles」的意圖，只是換成一個結構上保證做到的作法。
- 隱藏的 slot 用 `display: none` 自然塌陷，不留空洞 —— 這是「三者可同時出現」
  得以成立的機制。只有報告時，它就站在確認框原本的位置。

### 2.3 方向規則

| 條件 | class | 效果 |
|---|---|---|
| 視窗中心 y > 螢幕中心 y | `.flip` | `bottom` 錨定 + `flex-direction: column-reverse` |
| 視窗中心 x > 螢幕中心 x | `.lean-left` | `align-items: flex-start`（預設 `flex-end`） |

> ⚠ 見 §8.3 —— 這兩個 class 由誰掛、在哪個時機掛，本節未指定，而現行唯一的
> 呼叫點只在 toast 路徑上。沒有補上就等於原本「確認框不翻轉」的 bug 換個門走回來。

水平的「傾斜」不再用 `left: calc(50% - 20px)` 這類偏移。容器橫跨整個視窗寬
（左右各留 8px），泡泡靠 `align-items` 靠邊。於是 idle 176px 窄視窗與 large
320px 寬視窗共用同一份規則，不需要分支。

### 2.4 z 層級 — 三個值，兩條互斥規則

| 層 | z | 誰在裡面 |
|---|---|---|
| 外圈 | `900` | 確認框 / 報告 / 名牌（同一容器） |
| 狀態點 | `930` | 弧上的所有點 |
| 選單 | `1000` | 放射選單 |

狀態點壓在泡泡之上，確保它永遠可以被 hover —— 這是它比外圈高的唯一理由。

互斥規則只有兩條，明列在 `tokens.css` 而非散落各模組：

1. **選單開啟** → 狀態點隱藏（沿用現行 `body.menu-open`）；外圈降至
   `opacity .32` 並去飽和，**不隱藏** —— 讓人知道東西還在，只是被壓住。
2. **確認框開啟** → orb 退出 busy 動態並鑲上琥珀環（見 §4）。

> ⚠ 見 §8.2 —— 這兩條不夠。`.flip` 時中間的狀態點命中區會蓋住確認框的動作列，
> 而「點 930 > 外圈 900」這條規則讓點贏，「✓ 送出」的下緣因此按不到。

### 2.5 面板家族 — 有框＝可操作，無框＝只是在說話

| 面板 | 框 | 彈出 |
|---|---|---|
| 報告泡泡 · 名牌 | **無框**。深底 ＋ 頂緣受光 ＋ 外暗邊 | 從離 orb 最近的角 `scale(.34) → 1` |
| 確認框 | 琥珀框 ＋ 外暈 —— 全系統唯一有框的說話面板 | 同上，同一條曲線 |
| 放射選單 · 動作鈕 | 白細框 `rgba(255,255,255,.16)` | 逐項從中心飛出，同一條曲線 |

一條規則同時解掉兩件事：小泡泡不再帶一圈與確認框打架的白框；而畫面上
**「看得到框」永遠等於「這裡有你的事」**。這條規則和 §1 的兩軸配色是同一個
方向的收斂 —— 語意各自獨佔一種表徵，不共用。

彈出由兩個 token 統一：

```css
--ease-pop: cubic-bezier(0.34, 1.56, 0.64, 1);
--dur-pop:  220ms;
```

泡泡用 `@keyframes` 而不是 `transition`，這一點不能省：slot 是靠
`display: none` 塌陷的，而 `display` 的變化會吃掉 transition。animation 不會 ——
這是規範保證的行為，不是實作巧合：

> If an element has a `display` of `none` and its `display` value had computed to
> `none` when ignoring the Transitions and Animations cascade origins, updating
> `display` to a value other than `none` will **start all animations** applied to
> the element by the `animation-name` property.
> — [CSS Animations Level 2](https://drafts.csswg.org/css-animations-2/)

**為什麼不用 `transition-behavior: allow-discrete` ＋ `@starting-style`？**
那組也能做到，但要兩個較新的特性一起到位，而這是一個離線桌面 app，webview 版本
由使用者的 macOS 決定，我們無法要求。`animation` 是單一機制、規範明文、且在
WKWebView 上已經是所有 modal 開場動畫依賴的路徑。少一個賭注。

```css
@keyframes bubble-pop {
  from { opacity: 0; transform: scale(0.34); }
  to   { opacity: 1; transform: scale(1); }
}
```

`transform-origin` 依方向 class 落在離 orb 最近的那個角：

| 狀態 | `transform-origin` |
|---|---|
| 預設（朝下、靠右） | `top left` |
| `.lean-left` | `top right` |
| `.flip` | `bottom left` |
| `.flip.lean-left` | `bottom right` |

於是泡泡是**從式神身上長出來**，不是在旁邊淡入 —— 這是「一切從頭像長出來」
從原則變成一行 CSS 的地方。放射選單原本就是逐項從中心飛出，換用同一組 token
之後兩者的手感對齊；`menu.ts` 的 `50ms × i` stagger 不變。

## 3. 排版階梯

每一項都是有限集合。**這六個維度**上不在表內的值就是錯的。

| 維度 | 值 | 用途 |
|---|---|---|
| 字級 | `10 / 11 / 12 / 13` | 10 微型（＋N、動作鈕）· 11 標籤與按鈕 · 12 內文與輸入 · 13 保留 |
| 行高 | `1 / 1.35 / 1.5` | 1 按鈕單行 · 1.35 單行標籤 · 1.5 可讀內文 |
| 圓角 | `4 / 8 / 999` | 4 控制項 · 8 面板 · 999 點 |
| 間距 | `2 / 4 / 6 / 8 / 12 / 16` | 8 = slot gap · 6–8 泡泡內距 · 12–16 選單內距 |
| 模糊 | `10 / 18 / 22` | 10 面板 backdrop · 18 琥珀外暈 · 22 落影 |
| 字距 | `0.02em / 0.08em` | 0.02 小字標籤 · 0.08 全大寫選單 |

原本的 9/10/11/12px 與 4/5/6/10px 各降一級為四級與三級。9px 在等寬字下已經
接近不可讀，直接刪除。

**線寬與半徑不在這張表上，它們是幾何而非排版**，住在 §5：狀態點隔離環 1.5、
中空環 2.5、面板邊 1、pending rim 1.6 與外暈 3.5。把它們硬塞進排版階梯只會讓
「不在表上就是錯的」變成一句自己都守不住的話。

全大寫必須配 `0.08em` 正字距：等寬字全大寫沒有正字距會擠成一團。

## 4. 「正在忙」與「等你確認」必須長得不像

「正在忙」（麥克風準備中／辨識中／召喚中）不再開泡泡 —— 元素已經太多。
它由式神本體表達：**呼吸加速、輪廓收緊、褪色**。一隻專注的生物會屏息，不會舉牌子。

> ⚠ 見 §8.1 —— 這三個 stage 不等價。錄音中與召喚中各自帶著一個**只存在於那個
> 泡泡裡的資訊**（對誰說話、召喚哪個專案），一起收進 orb 會把它弄丟。

| orb 狀態 | 呼吸速率 | 半徑係數 | 輪廓抖動 | canvas 不透明度 | rim |
|---|---|---|---|---|---|
| 安靜 `idle` | `1.1 rad/s` | `×1.00` | `×1.00` | `0.55` | 白 25%，線寬 1 |
| 正在忙 `busy` | `2.4 rad/s` | `×0.90` | `×0.45` | `0.78` | 白 25%，線寬 1 |
| 說話 `speaking` | `1.1 rad/s` | `×1.00` ＋音量 swell | `×1.00` | `1.00` | 白 25%，線寬 1 |
| 等你確認 `pending` | `1.1 rad/s` | `×1.00` | `×1.00` | `0.92` | 琥珀 90%，線寬 1.6，外暈 alpha .35 線寬 3.5 |

**表中所有線寬都是「顯示座標」（120px canvas 的視覺尺寸），不是畫布座標。**
`avatar.ts` 在 `SIZE = 160` 的內部畫布上作畫，CSS 縮到 `120px` 顯示，所以：

```
canvas lineWidth = 顯示線寬 × (160 / 120) = 顯示線寬 × 1.3333
```

| 用途 | 顯示 | 代進 `ctx.lineWidth` |
|---|---|---|
| idle / busy / speaking rim | `1` | `1.33` |
| pending rim | `1.6` | `2.13` |
| pending 外暈 | `3.5` | `4.67` |

不標單位是會真的寫錯的：現行 `avatar.ts` 是 `lineWidth = 1` 在 160 畫布上，
顯示出來只有 `0.75px` —— 照表值直接填就會得到規格的四分之三粗細。
（`index.html` 規格頁用 240 畫布 ＋ `BASE_R 81` 是為了 retina 清晰度，
比例與 160 / 54 完全相同，換算係數是 `240 / 120 = 2`。）

兩者的心理狀態因此在視覺上互斥：

- **忙 = 收緊、褪色、快** —— 系統在動，你不用動。
- **等你 = 舒張、鑲金邊、回到正常速度** —— 系統停下來了，該你動。

三個係數各自以 `1 - exp(-6·dt)` 平滑趨近目標，不硬切。busy 的褪色以 `fade = 0.45`
把漸層三個 stop 往低飽和灰青插值，不換色相。

### 4.1 avatar.ts 的具體改動

```ts
// 新增
export function setBusy(on: boolean) { busy = on; }

// orbTargets()：三個係數
const tg = busy ? { speed: 2.4 / 1.1, radius: 0.90, wobble: 0.45 }
                : { speed: 1,         radius: 1,    wobble: 1    };

// radius()：kRadius 乘在 BASE_R 上。
// kWobble 乘在「不由音量驅動」的兩個抖動項上 —— idleW，以及 driven 裡的
// 0.06*sin(5θ) 那一項（原式沒有 * l，它其實是輪廓抖動而非嘴型）。
// 0.12*l*sin(3θ) 是真正的音量項，不受 kWobble 影響，否則說話時嘴型會被壓扁。
const driven = 0.12 * l * Math.sin(3*theta + wobA)
             + kWobble * 0.06 * Math.sin(5*theta - wobB);
// loop()：breathe += 1.1 * kSpeed * dt
```

### 4.2 動態關閉時（`prefers-reduced-motion: reduce`）

§1.1 說「任一維度失效都還剩三個」，這一節是把那句話兌現成規則。這套設計用呼吸、
心跳、彈出承載語意，是四個維度裡最容易被系統設定整組拿掉的一個 —— 沒有降級規則，
它就只是一句空話。

**靜態下四種狀態改用「尺寸階梯 ＋ 實心／中空 ＋ 明度」三個維度分開：**

| 狀態 | 動態開啟 | 動態關閉 |
|---|---|---|
| `idle` | 不呼吸 · `scale(0.72)` | 不變 —— 本來就是靜態 |
| `working` | 呼吸 3.2s · `scale(0.92 ↔ 1.14)` | 定格 `scale(1.00)` 實心 |
| `blocked` | 心跳 1.6s · 中空環 | 定格 `scale(1.00)` 中空環 2.5px |
| `done` | 靜止 · `scale(1.00)` 最亮 | **`scale(0.85)`** 實心最亮 |

`done` 從 1.00 收到 0.85 是這張表唯一的新值，理由是必要的：動態開啟時
`working` 與 `done` 靠「一個呼吸一個靜止」分開，動態關閉後這個維度消失，
兩者只剩 35° 色相差。收到 0.85 後四態變成一條尺寸階梯 —— **`0.72 / 0.85 / 1.00`
再加上 blocked 的中空**，即使全灰階、全靜止也能分辨。

**其他元素的降級：**

| 元素 | 規則 |
|---|---|
| 泡泡 `bubble-pop` | 只留 `opacity 0 → 1`，`120ms linear`，去掉 `scale` |
| 放射選單 | 去掉 `scale(0.3)` 與 `50ms × i` stagger，只留 opacity |
| orb 呼吸 | `breathe` 定格在相位 0（`kSpeed = 0`） |
| orb busy | **仍然可辨** —— 半徑 `×0.90`、輪廓抖動 `×0.45`、不透明度 `0.78` 三個都是靜態量 |
| orb pending 琥珀環 | 不受影響，它本來就是靜態的 |
| orb 說話嘴型 | 振幅減半，**不關掉** —— 它是「誰在說話」的資訊，不是裝飾 |

busy 能在動態關閉下存活不是巧合：§4 一開始就把它設計成三個靜態係數 ＋ 一個速率，
拿掉速率還剩三個。這是「多維度冗餘」在這套系統裡第二次付清帳。

```css
@media (prefers-reduced-motion: reduce) {
  .roster-dot::before        { animation: none !important; }
  .roster-dot[data-status="working"]::before { transform: scale(1); }
  .roster-dot[data-status="done"]::before    { transform: scale(0.85); }
  #aura > .show              { animation: aura-fade 120ms linear both; }
  #radial-menu button[role="menuitem"] { transition: opacity 120ms linear; }
}
@keyframes aura-fade { from { opacity: 0 } to { opacity: 1 } }
```

orb 是 canvas，所以這是唯一無法純 CSS 完成的部分。`avatar.ts` 的補丁：

```ts
// 讀一次就好 —— 使用者改系統設定會重啟 app，不需要監聽變更
const REDUCED = typeof matchMedia === "function" &&
  matchMedia("(prefers-reduced-motion: reduce)").matches;

// orbTargets()：速率歸零，但三個靜態係數原封不動 —— busy 因此仍然可辨
function orbTargets() {
  if (busy) return { speed: REDUCED ? 0 : 2.4 / 1.1, radius: 0.90, wobble: 0.45 };
  return { speed: REDUCED ? 0 : 1, radius: 1, wobble: 1 };
}

// radius()：音量項振幅減半（說話嘴型「減半但不關掉」）
const vol = REDUCED ? 0.06 : 0.12;
const driven = vol * l * Math.sin(3 * theta + wobA)
             + kWobble * 0.06 * Math.sin(5 * theta - wobB);

// loop()：逐一凍結「非音量驅動」的相位。
// wobA 必須繼續前進 —— 它只出現在 l 相乘的音量項裡，凍結它會讓嘴型僵掉。
breathe += 1.1 * kSpeed * dt;              // kSpeed 已是 0
idle    += REDUCED ? 0 : 0.7 * dt;         // 輪廓漂移
wobA    += 2.2 * dt;                       // 保留：說話嘴型
wobB    += REDUCED ? 0 : 1.4 * dt;         // 0.06·sin(5θ) 這項不受 l 控制，要凍
```

四個相位要分開處理而不是一起關掉，理由在 `driven` 的兩項結構不同：
`0.12·l·sin(3θ+wobA)` 被音量 `l` 乘住，靜止時本來就是 0；
`0.06·sin(5θ−wobB)` 沒有 `l`，永遠在動 —— 只關第一組會漏掉它。

附帶好處：`REDUCED && !active` 時畫面完全靜止，`loop()` 的 adaptive fps
可以進一步停止重繪（現行 idle stride 是 3）。這是省電，不是設計要求，
所以沒寫進上面的補丁。

（`54 + 內距 8 + 邊 2`）。這需要把 `command.ts:143` / `:245` 的

#### 為什麼不必拿「讀完」去換「變小」

收成 3 行的第一版讓長轉錄稿要捲動才讀得完，與硬原則「確認不可被省略」直接衝突。
但那個衝突的成因是**寬度不是高度** —— 確認框沿用了 `--bubble-max: 176px`，而
large 視窗有 320px 寬，`176` 之外的 **136px 從來沒被用到**。

所以確認框單獨加寬到 **248px**，其餘泡泡維持 176：

| 泡泡寬 | 內容寬 | 中文字／行 | 3 行可容 |
|---|---|---|---|
| `176`（原） | 148px | 12.3 | **37 字** |
| **`248`（現）** | 220px | 18.3 | **55 字** |

**容量 +49%，而高度、堆疊、視窗尺寸完全不動**（`120 / 286 / 592` 一個都沒變）。
水平也放得下：容器可用寬 `320 − 8 × 2 = 304`，泡泡靠邊後另一側仍餘 56px。

這不只是把數字調大 —— **「必須讀完的」比「只是在說話的」寬，本身就是階層**，
而且不齊的那一邊朝向遠離螢幕中心的方向，靠近中心的那一邊仍然對齊。

原本被當成取捨記在這裡的東西因此不存在了。真正剩下的限制是：超過 55 個中文字
（約 92 個拉丁字元）的轉錄稿仍會捲動。若那天真的到了，加寬到 288 可再拿到 65 字，
容器還餘 16px；再要更多才需要動視窗高度（每多一行 18px → 視窗 +36px）。

上下必須對稱，因為 `.flip` 會讓外圈朝上長 —— 兩個方向需要等量空間。
**寬度維持 320**，所以選單的水平夾取行為零變化。

```
slot_n 近緣 = 64 + Σ(前面每一個「可見」slot 的實際高度 + 8)
```

實際數值由 flex 在執行期求出 —— 這正是「隱藏就塌陷」的機制。下表是三者
皆達上限時的最壞情況，視窗高度就是照這組數字定的：

| 可見組合 | 確認框 | 報告泡泡 | 名牌 | 最遠緣 |
|---|---|---|---|---|
| 任一單獨出現 | `+64` | `+64` | `+64` | ≤ 184 |
| 確認 ＋ 報告 | `+64` | `+192` | — | 258 |
| 報告 ＋ 名牌 | — | `+64` | `+138` | 158 |
| 三者同時 | `+64` | `+192` | `+266` | **286** |

**orb 輪廓半徑的來歷**：`avatar.ts` 的 `BASE_R = 54` 是 160px 內部畫布上的值，
CSS 縮到 120px 顯示 → 實際輪廓 `54 × 0.75 ≈ 40.5px`。60px 是 canvas 盒子的半寬，
不是生物本體。錨點若用 60 會產生 20px 的空隙，讀起來像另一個視窗而不是氣場。

**名牌必須留在 idle 視窗帶內**（硬性條件）：

```
hover  態  88 − 64 − 19 = 5px 餘裕
選中態     88 − 64 − 20 = 4px 餘裕     →  兩態都不需要放大視窗
```

理由是 hover 是 `mousemove` 驅動的高頻行為。若它觸發 `acquireLarge()`，
`roster.ts:259` 的 `onFrameChange(renderStrip)` 會依新中心重算弧，點就從游標底下
移開，形成 hover → 放大 → 點跑掉 → mouseleave → 縮回 → 再 hover 的閃爍迴圈。

**選中態同樣不得放大視窗**，理由不同但一樣硬：`roster.ts:245` 的
`if (selEntry) showLabel(selEntry, true)` 會在每次 `renderStrip()` 重新掛回常駐
名牌，所以放大 → `onFrameChange` → 重算弧 → **剛剛點的那顆點瞬移約 200px**。
它不會來回震盪（選取是 sticky，不會 mouseleave），但弧在點擊瞬間跳位是實質的
視覺斷裂，而且 `roster.ts:263` 的點擊外部判定會拿到過期的命中區。

結論：**名牌的兩個狀態都必須塞進 176 視窗**，這反過來決定了動作鈕只能是 16×16。

> ⚠ **`box-sizing` 陷阱** —— 這是本輪唯一被實測抓出來的算錯。
> `src/styles.css` 沒有全域 `*` reset，預設 `content-box`，所以 `width: 16px`
> ＋ `border: 1px` 會算成 **18px**，名牌 row 從 20 撐到 **24**，餘裕歸零、落影
> 被視窗邊界裁掉。`tokens.css` 因此對 `#roster-label button` 明寫
> `box-sizing: border-box`。
>
> 只有它需要 —— 確認框與選單按鈕是 auto 高度（`box-sizing` 對 auto 無作用），
> 狀態點用 `inset` ＋ `box-shadow` 而非 `border`。逐一查過，不是猜的。

| `command.ts:214` | `⚡ 召喚 {project} 中…` | **專案名** | 約 10 秒的匿名忙碌 orb |
| （`onUtterance` 內） | `辨識中…` | 無 | **可以收** |

第二項是定位層級的退步，不只是 UX：1:1:N 產品裡「我正在對誰說話」是核心資訊，
把它延後到確認框才揭露，等於讓人**盲講一整句**。
`command.ts:87-89` 的既有註解也明寫停止 affordance 是刻意的：
「a running capture always has an on-screen stop affordance」。

第三項的問題是時長：herdr chain（`tab.create → agent.start → wait → prompt`）
約 10 秒，全程只有一顆無名的忙碌 orb。

**提案**：麥克風準備中與辨識中收進 orb busy；**錄音中與召喚中保留一個最小泡泡**，
用 §2.5 已經定義的「無框＝只是在說話」那一族，不需要新機制、不動 slot 預算
（兩者都佔 slot 1，且都與確認框互斥 —— 確認框出現時它們已經結束）。

**已決（2026-08-08）**：採折衷。§4 開頭那句改讀為「**沒有獨有資訊的 stage** 不再
開泡泡」。落地時 `command.ts:61` 與 `onUtterance` 內的 `辨識中…` 改呼叫
`avatar.setBusy(true)`；`command.ts:294`（錄音中）與 `:214`（召喚中）保留泡泡，
但改用 §2.5 的無框族群，不再是現在那個琥珀確認框的外觀 —— 琥珀仍然獨佔給確認框。

被否決的替代案：全部收進 orb、改由目標的狀態點鑲琥珀環表達「在對誰講」。
否決理由是它會讓琥珀出現在確認框以外的地方，鬆動 §1.2 那次收斂；而且召喚中
仍然沒有專案名可以掛。

### 8.2 [阻斷] `.flip` 時中間的狀態點壓在確認框的動作列上

新中心 `296` 下：

```
aura 底緣（.flip）  = 592 − (296 + 64) = 232      往上長，確認框動作列在 ~212–232
中間狀態點 y        = 296 − 66 = 230              20px 命中區 → 220–240
重疊                = 220–232，約 12px
```

而 §2.4 明訂狀態點 `z 930` > 外圈 `900` —— **點贏**。結果是「✓ 送出」按鈕的
下緣按不到，落在最不該失手的那顆按鈕上。外圈的點低約 12px 剛好閃過，
只有中間 1–2 顆會撞（`arcPositions` 依 `currentCenter()` 算，`roster.ts:202`）。

三條路：

| 解法 | 代價 |
|---|---|
| **A. 加第 3 條互斥規則**：確認框開啟 → `#roster-strip { pointer-events: none }` | 幾乎為零，且語意正確：確認當下該做的只有 ✓／✕。**建議** |
| B. `.flip` 錨點加大到 ≥ 80 | 破壞「上下對稱 286」的推導，視窗高度變成要重新決定 |
| C. 確認框開啟時把外圈提到 `940` | 與 §2.4「點永遠可 hover」的唯一理由直接衝突 |

A 也與 §2.4「互斥規則明列在 `tokens.css` 而非散落各模組」的作法一致 ——
它就是第 3 條規則，不是特例補丁。

**已決（2026-08-08）**：採 A。它是 §2.4 的**第 3 條互斥規則**，不是特例補丁 ——
`tokens.css` 補 `body.confirm-open #roster-strip { pointer-events: none }`，
由 `command.ts` 的 `showConfirm` / `showSummonConfirm` / `hideConfirm` 掛卸 class。

注意只停 `pointer-events`，**不隱藏**：確認期間仍然應該看得到誰在工作，
與 §2.4 第 1 條「不隱藏，讓人知道東西還在」同一個取向。

### 8.3 [阻斷] `.flip` / `.lean-left` 沒有人負責喊

§6 寫「`toast.ts` 的 `place()` 改為只計算兩個 class 並套在 `#aura` 上；
`command.ts` 與 `roster.ts` 不再各自定位」。但 `place()` **目前唯一的呼叫點是
`toast.ts:53`，在 `toast()` 內部** —— 只出現確認框、或只出現名牌時，沒有任何人
設定方向 class，於是它們永遠用預設方向。

這正是本設計要殺掉的「確認框完全不翻轉」那個 bug，從另一個門走回來。

**提案**：把 `place()` 抽成獨立的 `orient()`（住在自己的模組，或留在 `toast.ts`
但 export），在 `toast()`／`showConfirm()`／`showSummonConfirm()`／`showLabel()`
四個 show 點都呼叫。

**不能只掛 `onFrameChange`**：使用者拖動視窗會改變答案，而拖動不觸發 frame change
（`window-frame.ts` 只在尺寸切換時通知）。方向必須在每次「要顯示」時重算。

### 8.4 [成本，本輪不處理] 每一則 agent 報告都會把視窗吹到 592

`agent:report` 是外部隨時推送的（`main.ts:23`），不是使用者觸發的。
所以**每一則報告都會讓視窗維持 `320 × 592` 至少 3 秒**（`toast.ts` 的
`HOLD_MS = 3000` ＋ 打字時間），透明但仍攔截滑鼠的區域比現在的 `320 × 360`
多快一倍 —— 而單一 toast 其實只需要約 300px 高。

§「已知代價」把這筆成本記成「三件事可同時說話的直接成本」，但實際上
**最常見的情境是只有一件事在說話**，卻付了三件事的價。

ref-count 已經知道哪些 slot 被持有，要做「只有 toast 時用中等尺寸」是可行的
（`window-frame.ts` 從兩段式變三段式）。

**已決（2026-08-08）：本輪不做，另行開票。** 它是獨立的窗框優化，與視覺語言
統一沒有因果關係，綁同一個 commit 會讓 diff 說不清楚。先讓 592 落地，
之後再單獨處理三段式。
